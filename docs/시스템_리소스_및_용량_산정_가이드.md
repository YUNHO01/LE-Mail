# 📊 LEMail 시스템 리소스 및 용량 산정 가이드

본 문서는 LEMail 엔터프라이즈 메일 플랫폼을 도입·운영하는 기업의 **사용 인원 수(100명 ~ 10,000명 이상)**에 따른 서버 하드웨어 사양, 인프라 아키텍처, 네트워크 대역폭, 스토리지 및 데이터베이스/캐시 용량 산정 가이드를 제공합니다.

---

## 1. 리소스 산정 기준 모델 (Traffic Modeling)

엔터프라이즈 비즈니스 환경의 평균 메일 이용 통계를 기준으로 수립되었습니다:

| 항목 | 일반 비즈니스 기준치 | 비고 |
| :--- | :--- | :--- |
| **1인당 일일 수신 메일** | 30 ~ 50통 | 스팸/마케팅 메일 필터링 전 유입량 기준 |
| **1인당 일일 발송 메일** | 10 ~ 20통 | 내/외부 발송 합계 |
| **메일 1통당 평균 크기** | 100 KB ~ 250 KB (본문) | 대용량 첨부파일 제외 기본 크기 |
| **첨부파일 포함 평균 크기** | 1.5 MB ~ 3.0 MB | 업무용 첨부파일(PDF, 이미지, 문서) 포함 가중 평균 |
| **동시 접속률 (Concurrency)** | 20% ~ 30% (평시) / 40% (피크) | 웹메일 브라우저 탭 유지 + 모바일/PC IMAP IDLE 유지 |
| **기본 사서함 할당량 (Quota)**| 5 GB ~ 20 GB / 인 | 정책에 따라 유동적 적용 |
| **보관 연한 (Retention)** | 1년 ~ 3년 | 규정 준수(Compliance) 및 백업 정책 기준 |

## 3. 세부 컴포넌트별 튜닝 가이드

### 3.1 Web & Core API 서버 (`apps/api`, `apps/web`)
- **Piscina Worker Pool 튜닝**:
  - 대량 인바운드 메일 파싱 시 CPU 바운드 작업을 처리하는 스레드 풀 크기:
    $$\text{Piscina Thread 수} = \text{vCPU Core 수} \times 1.5 \sim 2$$
  - 예: 8 vCPU 인스턴스 ➔ `PISCINA_MAX_THREADS=12 ~ 16`
- **Node.js 힙 메모리 할당 (`max-old-space-size`)**:
  - 대용량 EML 스트림 및 첨부파일 버퍼링을 고려하여 Node 프로세스당 최소 4GB~8GB 권장:
    ```bash
    NODE_OPTIONS="--max-old-space-size=8192"
    ```

### 3.2 IMAP 데몬 (`services/imap`)
- **TCP Connection 및 소켓 버퍼**:
  - IMAP IDLE 유지 클라이언트는 연결을 상시 유지하므로 OS 파일 디스크립터 한도(`ulimit -n`)를 반드시 상향 조정:
    ```bash
    # /etc/security/limits.conf
    * soft nofile 65536
    * hard nofile 131072
    ```
- **메모리 소비량 추정**:
  - 클라이언트 세션 1개당 약 50 KB ~ 150 KB의 메모리를 점유합니다.
  - 1,000명 동시 연결 시 약 150 MB, 5,000명 동시 연결 시 약 750 MB 수준으로 Node.js 기반 메모리 효율성이 매우 뛰어납니다.

### 3.3 MySQL 데이터베이스 (`my.cnf`)
- **InnoDB Buffer Pool Size**: 전체 물리 메모리의 60% ~ 70% 할당 (메타데이터 및 인덱스 캐싱)
- **Max Connections**:
  $$\text{max\_connections} = (\text{API 인스턴스 수} \times \text{Pool Size}) + (\text{IMAP 인스턴스 수} \times \text{Pool Size}) + 50$$
  - 1,000명 규모: 최소 300 ~ 500
  - 5,000명 규모: 최소 1,000 ~ 1,500
  - 10,000명 규모: 최소 2,000 ~ 3,000

```ini
# MySQL 8.0 권장 설정 (16GB ~ 64GB RAM 기준 예시)
[mysqld]
innodb_buffer_pool_size = 45G         # RAM의 70% 수준
innodb_log_file_size = 4G
innodb_flush_log_at_trx_commit = 2    # 고속 메일 색인 처리 (배터리 백업 캐시 환경)
innodb_flush_method = O_DIRECT
innodb_file_per_table = 1
max_connections = 1500
open_files_limit = 65535
table_open_cache = 8000
```

### 3.4 스토리지 구조 및 IOPS 요구사항
메일 시스템은 특성상 **작은 크기의 파일(EML 원문, 개별 첨부파일)이 빈번하게 생성/조회**되는 무작위 I/O(Random Write/Read) 패턴을 보입니다:

1. **`mail-spool/`**: 고속 NVMe SSD 필수 (Write Intensive, 메일 유입 즉시 임시 기록 ➔ 파싱 후 삭제)
2. **`mail-archive/`**: 엔터프라이즈 NAS/SAN (NFS v4) 또는 Ceph/GlusterFS 분산 스토리지. 월별 디렉터리(`YYYY-MM`) 구조로 분할되어 디렉터리당 inode 포화 방지.
3. **`mail-attachments/`**: UUID 기반 2단계 하위 디렉터리 분산 저장(예: `/ab/cd/uuid_filename`)을 적용하여 파일시스템 병목 최소화.
